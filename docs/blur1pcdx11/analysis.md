# Analysis (Blur1PCDX11): the native Direct3D 11 renderer

### T127: Direct3D 11 branch and renderer boundary (2026-09-26)

`blur1pcdx11` is a branch and worktree at `Blur1PCDX11/`, created from `blur1pc` commit `547ccfb1`. `DeviceDefines.h` selects `DEVICE_PCD3D9` for the PC build, `Display::C_Device` inherits `C_PCD3D9Device`, and a text search found 406 matching `D3D9` or `DEVICE_PCD3D9` lines in display headers. The D3D9 device owns render targets, textures, buffers, shaders, draw states and presentation; a new backend requires matching these interfaces and the `Display2` path before `Amax` can select it. `shadergen.py` emits `vs_2_0`/`vs_3_0` and `ps_2_0`/`ps_3_0` bytecode blobs. The retail `.fxb` importer reads a `PCFX` section and the engine creates D3D9 shaders from the effect microcode; that bytecode is not a Shader Model 5 program.

The branch's `blur_dx11` module creates an actual feature level 11 hardware or WARP device, renders with the repository's `vsBasicRenderColoured2D.vsh` and `psBasicRenderColoured.psh` compiled for Shader Model 5, and reads the target back. Both paths returned center RGBA `(125,67,63,255)` and untouched corner `(5,10,20,255)` at 64x64. The first SM5 pixel compile failed on D3D9's `COLOR0` output; an `SV_Target` variant fixed that. The first draw after that produced black because the vertex and pixel color signatures occupied different hardware registers (D3D11 debug layer's `Draw` validation message). Putting the DX11 vertex color output before `SV_Position` gave matching register positions and correct pixels. The shader changes are conditional on `BLUR_DX11`; `shadergen.py` still compiled 693 built-in SM3 variants with zero failures. The game's D3D9 backend has not been replaced or run in this branch.

The native module now also creates and resizes a DXGI swap chain, uploads PC BGRA texture data and samples it, allocates vertex/index and depth resources, and uses SM5 reflection to bind the existing 2D clip vector and 3D world/view-projection matrix parameters by name. Hardware and WARP probes drew the repository's 2D colour, 2D textured and 3D colour shaders and passed readback checks, including a translated 3D triangle. The DX11 debug layer reported no validation messages in those runs. `BLUR_USE_DX11=ON` was attempted for `Amax` but cannot compile yet because the native Display and Display2 backend types are absent; the D3D9 fallback (`BLUR_USE_DX11=OFF`) `Amax` build finished with zero errors. The branch now defaults to DX11 selection so it does not silently build a D3D9 game. The source `.fx` files use D3D9 effect syntax, including `texture2D`, `sampler_state` and `tex2D` calls, so the retail effect shader path needs a real SM5 source conversion/recompile step in addition to a native renderer. There is no playable DX11 executable from this branch yet.

### T127: native DX11 effect and resource continuation (2026-09-26)

The original PC shader Jam rules generate 1,254 uniquely named effect variants from 108 `.fx` entries. All 1,254 compile to FX5 after preprocessing with the PC build defines, replacing SM3 compile profiles, removing FX9 `shared` and conflicting register declarations, and changing pass syntax to `technique11`. The native branch vendors Microsoft's FX11 source (MIT) and loads those FX5 binaries by the original effect filename. All 1,254 were preloaded successfully by FX11 on hardware and WARP. A `ScreenFacingSprite` Material pass draws an indexed triangle through FX11 and readback shows white center pixels on both. The game still imports PCFX/D3D9 effects through `FX::Manager`; its native path is pending.

The authored FX9 pass assignments found in these variants comprise `AlphaBlendEnable`, `AlphaTestEnable`, `SrcBlend`, `DestBlend`, `BlendOp`, `AlphaRef`, `ZWriteEnable` and `CullMode`. The FX5 compiler emits native blend, depth and rasterizer state objects for the supported values; an FX11 `MeshEffect` pass was checked through D3D11 state getters. The base display `C_ContextBase::SetAlphaTestState` sets a greater-than test, so alpha-tested pixel entries receive an SM5 discard at `(AlphaRef + 0.5)/255`; disassembly of `AutoScrollFade` confirms a discard instruction. The half-step float threshold is a DX11 approximation of D3D9 fixed-function alpha quantization, not a retail pixel comparison. Every effect sampler in the PC variants uses point for all min/mag/mip filters or linear for all three, so the compiler emits a native `Filter` property. Sampler sRGB flags are kept in a sidecar and selected as sRGB DXGI texture views when binding. The FX11 Material pass bound a linear sampler in the probe.

The native resource probe also creates 3D and cube textures, samples known BC1/BC2/BC3 blocks and an sRGB BGRA texture, and creates multisampled color/depth targets and resolves color. Hardware and WARP with the D3D11 debug layer passed. The reusable device now draws indexed FX11 passes using the game's vertex element metadata, but the Display/Display2 backend and game window integration remain unimplemented, so no DX11 Amax executable exists.

The separate Jam-selected built-in shader list has 693 variants. A native compiler pass with FXC backwards-compatible HLSL syntax and SM5 produced all 693, preserving authored source files and removing only the explicit SM3 c-register assignments from generated preprocessed copies. One UI pixel shader needed a float4 `SV_Position` input under `BLUR_DX11`. The native probe loads `.cso` binaries for its 2D and 3D draws rather than compiling their source on each draw. Compilation and isolated draws are verified; the game Display binding path for those binaries remains pending.

### T127: game runs under DX11; stage signatures, threading and the vehicle shader gap (2026-09-28)

The native backend now runs `Amax` from retail PC data and reaches the start screen (`Intro\StartScreen.lua`), but the screen is black: neither the scene nor the UI reaches the swap chain. Four faults were found and three fixed.

**Threads.** The engine uploads textures and buffers from its loading thread while the main thread renders. D3D9 serialised that inside its runtime; D3D11 does not, and the debug layer reported `ID3D11DeviceContext::End: Two threads were found to be executing functions associated with the same Device[Context] at the same time` (corruption severity) with the device removed (`DXGI_ERROR_DEVICE_REMOVED`, Windows logged an `nvlddmkm` event 153) seconds later. Fixed by enabling `ID3D11Multithread::SetMultithreadProtected(TRUE)` on the immediate context right after device creation, the synchronisation the debug layer itself points at.

**Stage linkage.** D3D11 matches a vertex shader's output registers against the pixel shader's input registers; D3D9 matched by semantic name, so the authored shaders declare their interpolants in orders that collide under SM5. `/Gec` gives `SV_Position` register 0 in a vertex shader, pushing every interpolant up by one, while a pixel shader that does not declare a position starts at 0. The debug layer reported 150k `ID3D11DeviceContext::Draw: ... Signatures between stages are incompatible` messages and the draws were rejected. Fixed in the shader sources under `#if defined(BLUR_DX11)`, keeping the D3D9 declarations untouched: **a vertex shader emits its interpolants first and `SV_Position` last, and a pixel shader declares its inputs in the same relative order, with no position input.** Applied to `vsDefault_XY`, `vsFontRender`, `vsBasicRenderTextured3D`, `vsMultiTexture`, `vsFontEffects`, `vsPolygonStroke`, `vsPolygonTrail`, `vsFont`, `vsPrimitive2D/3D/Tex2D`, `vsTextureViewer`, the five `effect/shaders/sky` domes and the fourteen post-process pixel shaders that declare a `VS_OUTPUT` with the position first (`psWeightedFilter*`, `psGreyscale`, `psSepia`, `psTint`, `psMotionBlur`, `psShowDepth`, `psStatic`, `psSunRays`). `psFontEffects` gained the `TEXCOORD3` slot its vertex shader writes before `TEXCOORD0`. `psPolygonPaint` and `vsPolygonPaint` keep the mirrored convention (position first in both). The debug log then held no linkage error at all.

**Render target and depth size.** `BindRenderTargets` bound the stored depth surface whatever the colour target; D3D9 allowed a larger depth buffer, D3D11 does not (`The RenderTargetView at slot 0 is not compatible with the DepthStencilView` for the 640x360, 320x180, 160x90 and 80x45 downsampled targets against the 1280x720 depth). The depth view is now created only when the dimensions and sample counts match. This is an approximation of D3D9's larger-depth-buffer behaviour, not a copy of it.

**RestoreWindow.** Retail 0x005acac0 renders the window texture as a quad only when the engine's current colour surface is the back buffer, and copies it into the current surface otherwise (`StretchRect`, skipping a self-copy). The port drew the quad unconditionally. It now follows the retail branch: quad on the back buffer, `CopyResource` otherwise when the formats and sizes match, the quad again when they do not. Traced: the copy path is the one the running game takes (window texture `0ACF558C` into `10DA14A4`), the quad path only in the first frames.

**The vehicle effects have no source.** The FX5 replacement compiles the authored `.fx` sources and looks a pass up by its retail technique name (`NativeFX11Shader`). Comparing the technique names the engine reads out of the loaded retail `.fxb` files with our compiled FX5 set, 18 of the 26 effects loaded in a start-screen run match exactly (including `Default`'s 8 and `Advert`'s 3); the 8 mismatches are all the vehicle effects, and they are systematic: `veh_default`, `veh_matt`, `veh_glass`, `veh_paint`, `veh_paintM`, `veh_alpha`, `veh_neon`, `veh_alloy` and `veh_light` each ship ten techniques (`Material`, `MaterialNoDamage`, `MaterialAlphaLuminance`, `MaterialAlphaLuminanceNoDamage`, `MaterialLOD`, `MaterialNoDamageLOD`, `MaterialAlphaLuminanceLOD`, `MaterialAlphaLuminanceNoDamageLOD`, `MaterialPrepass`, `MaterialPrepassNoDamage`) while our `vehicle_common.h` declares five (`aHACK`, `Material`, `MaterialAlphaLuminance`, `MaterialLOD`, `MaterialAlphaLuminanceLOD`). `MaterialPrepass`, `MaterialPrepassNoDamage`, `MaterialNoDamage` and the rest appear nowhere in the source tree: the shipped vehicle shaders are a later revision than the leaked snapshot. Consequence, measured: every vehicle pass fails (`ID3D11Effect::Apply` returns `0x80070490`, `ERROR_NOT_FOUND`), no vertex shader is bound, and `DrawIndexedPrimitive` drops the draws (`DX11 indexed draw without VS ... lastFX=veh_default / MaterialPrepass`); 64 vehicle draws per frame at the start screen, where the car is the only 3D content. The retail microcode for those passes exists in the `.fxb` before the engine frees it; `System::OnEffectLoad` now dumps it to `_work/build/fxdump/<effect>_<technique>_<pass>_<vs|ps>.bin` (capped at 40 files) so the passes can be reconstructed. `veh_alloy / MaterialPrepass` is 876 bytes of vertex shader and 324 of pixel shader.

**Open.** The back buffer is black at every stage, including after `Quad::DrawFullScreenColour` proves the quad path, the window texture and the readback all work in isolation; the composite that should put the frame there has not been found. Opening a debug race (`Ui.NewLaunchMode` = `DebugRb`, Right Ctrl then Enter) crashes in `UI::C_UiManager::LoadingTextureClone` on a null source before the loading screen appears. Texture upload still trips `CopySubresourceRegion ... unaligned to a block ... BC1_UNORM requires alignment of {4, 4, 1}` for standalone block-compressed mips.

**Diagnostics kept.** The D3D11 debug layer raises SEH 0x87D on error-severity messages and stores warnings too, which floods the queue; `PCD3D11GameDevice` now filters warnings out of the info queue and installs a vectored exception handler that logs the queued messages before the crash handler runs. Draws with no bound vertex shader are skipped rather than raised on (`TryDraw`), and the rejected draw names the failed effect and technique.

### T127: the frame renders; only the prime to the back buffer is missing (2026-09-29)

A debug race launched from the start screen (Right Ctrl, Enter) runs to `Blur2PC.RaceState() == "Racing"` with a validation-clean debug layer, and the screenshot of the **window render texture** (`<shot>.window.tga`) is a complete frame: road with markings, trees, the HUD, tyre marks. The screenshot of the **back buffer** at the same moment is pure black. Everything up to the last step works; nothing presents.

`C_PCD3D11GameDevice::RestoreWindow` is the step that is meant to do it, and it now follows retail 0x005acac0: on the back buffer the window texture is drawn as a full-screen quad, on any other surface it is copied (`CopyResource` when the sizes and formats match, the quad otherwise). Counter on a 22-second race: `RenderSplitscreenWithoutAA` runs 2,221 times and binds the back buffer 5,041 times, `RestoreWindow` takes the copy path 541 times and the quad path **zero** times. `RenderSplitscreenWithoutAA` (ApplicationBase.cpp:1783) binds the back buffer immediately before calling `RenderSplitscreenViewWithoutAA` for each view, so the current surface changes again between that bind and `RestoreWindow`: measured at the check, the engine's colour surface is `1150D390` (texture `127E8BE4`, a post-process target), the back buffer is `02435A3C` (`05AB1AA4`) and the window is `024406D4`. Between the two calls the only work is `BeginRenderSplitscreenWithoutAA()`, the layer message whose handler is `C_GameWorldPostProcess::BeginRenderSplitscreenWithoutAA` (PostProcessLayer.cpp:197), so a layer is rebinding the target. On D3D9 that would put retail into the same `StretchRect` branch, which is why the D3D9 build has to be instrumented the same way before the port can be changed: the comparison is the next step (`tools/build.sh` with `BLUR_USE_DX11=OFF` in a second build directory, a bind trace in `PCD3D9Device`).

Two faults found on the way, both fixed: `Display2::CloneTexture2D` fell into its non-D3D9 branch, `memcpy(pDst->GetAddress(), pSrc->GetAddress(), ...)`, where both addresses are null on D3D11 — this crashed `UI::C_UiManager::LoadingTextureClone` the moment a race's loading screen cloned a texture (fixed with a `DEVICE_D3D11` branch that copies on the GPU; note display2 uses `DEVICE_D3D11`, not the display library's `DEVICE_PCD3D11`). The vehicle `MaterialPrepass` failure from the entry above also shows here: four `veh_alloy / MaterialPrepass` draws a frame are dropped, which is the hole where the car should be in the window screenshot.

### T127: the post-process chain is what swallows the frame (2026-09-29)

The presentation path is not `RestoreWindow` alone. Retail's order is: the game renders into the window texture, `RenderSplitscreenWithoutAA` binds the back buffer, `RenderSplitscreenViewWithoutAA` sends `BeginRenderSplitscreenWithoutAA` (which calls `PostProcess::C_Manager::Begin` and binds the chain render texture), then `RestoreWindow` puts the window texture into that chain texture (the copy path, see the entry above), then `EndRenderSplitscreenWithoutAA` runs the chain, and the last link, `I_PostProcess::DisplayFinal` with `E_Type_Final` (Interface.cpp:21), calls `RestoreColourSurface` (binds the back buffer), `RestoreViewport`, `SetFinalQuadSettings`, draws its texture full screen and clears the manager's `m_bActive`. That clear is why `C_Manager::End`'s own final quad never runs when post-processing is on — its block is skipped by design, not by a fault.

Measured switch: with `Graphics.Render.PostProcess.Enable` set to false in the game's `debug_values.xml`, the same race presents (`race2.tga` mean 44.8, 48% pixels drawn against 0.0 with post-processing on) while `<shot>.window.tga` is unchanged at mean 104. So the scene, the window texture, `RestoreWindow`, the back-buffer bind and quad drawing are all correct; the fault is inside the post-process chain between `Begin` and `DisplayFinal`. The file was restored afterwards.

Two things seen in that run: the frame is much darker without the chain (expected: no HDR resolve or tone map), and a white quad sits over the car — the hole left by the missing vehicle `MaterialPrepass` (the entry above), which the deferred lighting pass fills with white.

Next: instrument the chain's passes (`I_PostProcess::DisplayIntermediate` order, the chain texture each one samples and writes) with a captured texture per link, since the same class of fault as the built-in stage signatures is likely — the chain's shaders are the `psWeightedFilter*`, `psGreyscale`, `psSepia`, `psTint`, `psMotionBlur`, `psShowDepth`, `psStatic`, `psSunRays` pair set.

### T127/T149: four faults between the renderer and the screen (2026-09-29)

Found with a one-frame draw trace (`BLUR_DX11_TRACE_AT=<seconds>`, optional `BLUR_DX11_TRACE_PX=<fx>,<fy>`; with `BLUR_DX11_DEBUG=1` each draw also lists the debug-layer messages it raised). Each traced draw logs its shaders, the FX pass, the target, blend state and one pixel of the target after the draw. All four are fixed; the start screen and a debug race now present.

1. **Texture registers of the built-in shaders.** The SM5 recompiles keep D3D9's `sN` sampler registers, but fxc packs the texture of each legacy `sampler2D` into `t0, t1, ...` in order of first use. The final tone-map shader (`s0, s3, s5, s7, s8`) had its textures at `t0`-`t4`, so the texture set for stage 3 (bloom, 2D) landed in `t3`, which that shader declares as its 3D colour lookup; the sample returned 0 and the whole output was black. `C_D3D11GameDevice` now reflects each built-in shader once (keyed by the DXBC checksum), maps sampler stage N to the texture register of the same-named resource (stage N to tN for a texture with no matching sampler) and binds through that map in `SetTexture`, `SetVertexTexture`, `SetPixelShader` and `SetVertexShader`. FX11 effects bind by name and are unaffected.
2. **`Unbind`.** `C_D3D9Device::Unbind` (D3D9Device.cpp:397) releases shaders, the vertex declaration, the streams, the index buffer and the textures only. The D3D11 port called `ID3D11DeviceContext::ClearState`, which also drops render targets, viewport, samplers, blend, depth and constant buffers. The UI calls it before drawing (`ui/Graphics/PostProcess.cpp:92`), so every UI draw of a frame ran with no render target: the start screen was black although the scene and the final post-process pass had written the back buffer. Now a line-for-line port of the D3D9 function.
3. **FX texture values are native resources.** `nglFXParam_Sampler::Texture` and immediate texture parameters hold a `GPUTexture*` (`pGpuData`), which Display2 types as `ID3D11Resource` under D3D11 (and as `IDirect3DBaseTexture9` under D3D9, where `Context_Singlethreaded::SetTexture` passes it straight to `IDirect3DDevice9::SetTexture`). The FX11 bridge read it as a `Display::C_Texture*` and took its `m_pd3dTexture`, which is always null for such a pointer, so no effect ever received a texture and every material sampled zeros. Separately, the engine names a function binding by its texture parameter (`g_tAlbedo`) while `effects.samplers` was only indexed by sampler (`AlbedoSampler`); `C_D3D11EffectLibrary::TextureForSampler` now also resolves texture names.
4. **Half-pixel offset.** `Display::Quad` (render/Render.cpp) moved every full-screen quad by D3D9's half pixel (`scale / viewport size` in clip space). D3D11 samples pixel centres at half-integers, as PS3 does, and the engine already skips the shift on PS3. Under D3D11 it misaligned every post-process quad by half a pixel, and on a 1x1 target it put the quad's edge on the only pixel centre, so `LuminanceFinal`, `DepthCentreTap` and `LuminanceAdapted` wrote nothing; the adapted luminance stayed 0 and the tone map blew the image out to white. The shift is now skipped under `BLUR_USE_DX11` as under `PLATFORM_PS3`.

The debug-menu key has to come some seconds after the start screen appears now that its fade-in renders: `_work/run/scripts/race.txt` presses Right Ctrl 6 s after the screen (at 2 s the menu did not open in one run of three).

**Still wrong (measured on `_work/run/scripts/start2.tga` and `race2.tga`).** The start screen matches the D3D9 reference except the car, of which only the tyres draw (T148: the vehicle body techniques are missing from the recompiled effects). In the race the HUD, mirror, buildings and far road are right, but the near road and ground render near white: the trace at (0.70, 0.83) shows `Road / MaterialLights` writing `f4ffff` over a light-buffer texel with no light, so one of that shader's inputs (albedo, world normal, specular, screen reflection, environment, fog) is wrong; not identified yet. sRGB reads are not implemented: `SetTextureGamma` stores the flag only, the FX bridge never consults `TextureUsesSRGB`, and textures are created with UNORM formats, which do not allow `_SRGB` views (that needs TYPELESS creation).

### T127: fresh visual baseline and ignored technique defines (2026-09-29, Codex)

A fresh minimized, queued run of the delivered `517ebfec` executable, launching the debug race and capturing one still eight seconds into Racing, shows that the visual faults extend beyond the near road. `_work/run/scripts/visual_assessment.png` (converted from the game's TGA) shows most foreground surfaces washed out, large white/dark patches on buildings, missing foliage detail, badly rendered sky, scene strips outside the mirror, and no vehicle body. The HUD is readable. A matching queued run of `Blur1PC/_work/run/Amax.exe` produced `_work/run/scripts/visual_reference.png`: the same track and stationary camera show properly textured buildings, trees, road, barriers, sky and car. The reference is 1920x1080 while DX11 is 1280x720; this is a visual comparison, not a pixel-identical test. Both runs exited with code zero. Earlier claims that the buildings and mirror were right do not describe this fresh baseline; the branch README also still described an unbuildable game before this continuation.

The source exporter explicitly adds technique annotations to the shader compiler flags in `Fx_export.cpp:WriteEffect` through `GenerateAnnotationCmdLineParams`, and adds pass annotations in `WritePass`. The native `compile_fx.py` previously preprocessed each Jam variant only once and retained each technique's `Define` as inert FX11 metadata. For example, `Road / MaterialLights` did not compile with `ENABLE_LIGHTING_PREPASS`, and `MaterialLOD` did not compile with `LOD`. This is a verified compiler discrepancy, not yet proof of which visual symptom it causes. The continuation compiles separate FX11 effects for annotated techniques, selects them by effect and technique name, and uses the selected technique's sampler metadata. The current authored PC shader set has no pass-level `Define` annotation requiring a separate pass permutation (the `Invalid.fx` pass annotation is `Script`).

All 1,254 source variants compiled, producing 5,196 indexed entries. Hardware and WARP probes preload the complete set and reflect a `DynamicLightsSampler` texture binding in the selected road lighting pass (the legacy sampler syntax names both the texture and sampler `DynamicLightsSampler`, with different resource types). The probe initially failed its material draw because `DrawGameEffectIndexed` passed an isolated IA signature to `CreateGameInputLayout`, whose newer implementation uses `D3DReflect`. Passing full vertex shader bytecode restores the material draw, layout caching and remaining probe checks.

Two further bridge discrepancies were corrected: `FX::Context::ApplyBinding` now updates the current FX11 pass by parameter name when shared groups change, rather than using retail FX9 register numbers; the native device's legacy constant-buffer binder no longer overwrites FX11's reflected buffers while a native effect is active. The normal race remained extensively distorted after these changes. Temporary diagnostics showed sensible fog/exposure values and distinct per-material texture resources under expected names; this does not prove their samples or GPU constants correct.

`C_ContextD3D11::SetTexture` and `SetVertexTexture` bypassed the device's reflected sampler-to-texture map, assigning raw resources directly to tN. They now use native-resource entry points on the game device that share the mapping and retained-view state of its ordinary texture setters. **Measured visual improvement:** the clouds/sky texture reappears in `_work/run/scripts/visual_context.png`. The foreground remains white and buildings and mirror remain severely wrong. The road's planar reflection was suppressed for one diagnostic run only (`visual_no_reflection.png`); the foreground still washed out. Its window render texture (`visual_window.png`) already contains white foreground and duplicated mirror strips before final post-processing. Thus a road reflection sample alone, or only the final tone-map pass, does not explain the scene fault. The suppression and parameter-dump code were removed afterwards.

Next investigation: isolate the road's albedo/diffuse inputs in the pre-post-process window frame, validate the texture contents and effective resource/sampler/constant-buffer bindings at a draw, and implement the declared sRGB sampling contract. Do not describe the main scene as fixed on the strength of a clean debug layer or probe alone.

### T148: exact vehicle permutations and retained streamed values (2026-09-29, Codex)

The internal serialized `Effect::Name` is **not** a permutation identity. Different loaded FXB filenames share it. The native bridge formerly selected every such effect by that internal name, and the original microcode dump overwrote different permutations under the same basename. Initial recovery of those unkeyed dumps produced a black, incomplete body; those generated sources were discarded, not used as a fallback. `Manager::LoadEffectInternal` now retains the actual filename before `ImportFXB` invokes `OnEffectLoad`, in a DX11-only runtime member excluded from serialization. Native effect and sampler metadata lookup use that filename, preserving its permutation suffixes. This affects scene effects as well as vehicles and leaves the inherited D3D9 path unchanged.

An opt-in `BLUR_DX11_DUMP_VEHICLE_FX=1` Showroom run captured 2,048 shader binaries into `_work/build/fxdump_variants/`: 102 distinct vehicle material permutations with ten techniques each (2,040 shaders), plus eight vehicle-shadow shaders. `recover_vehicle.py` translates the material instructions into native-only FX5 HLSL, retaining CTAB uniform names as register-sized float4 arrays, source instruction comments and original binary hashes. Unsupported operations, missing constants or sampler metadata cause failure. It handles the captured arithmetic, swizzles, indirect control-point indexing and texture instructions; it does not alias absent techniques onto approximate ones. The control-point TEXCOORD4 input is integer, followed by numerical conversion, matching the authored U8_4 declaration and D3D9's conversion. A common VS/PS interface preserves texture-coordinate locations. Recovered effects use retail FXB pass states through the existing engine; full alpha-test parity remains a separate native-renderer gap. Uncaptured permutations still use authored sources and are not claimed recovered. The eight shadow captures were not substituted.

The authored FX conversion also missed typed `sampler2D`, `sampler3D` and `samplerCUBE` declarations when writing texture-name/sRGB sidecars; it now records them. These flags are metadata, not a claim that the game's sRGB view path is implemented.

GPU buffer readback exposed a second bridge gap. `GetImmediateParameter` used D3D9's `DoesSharedParameterConflict` optimization to omit copies of streamed shared values: that API relies on the global hardware register file retaining them. FX11 has separate effect buffers. The DX11 context now retains every shared immediate value so later BeginPass calls seed native buffers with the latest instance data. Before this change, a traced vehicle draw had zero vehicle vertex/pixel parameters and damage colours; afterwards vehicle matrices and damage colours were populated, and a traced main material had nonzero alpha/exposure. A bounded `BLUR_DX11_TRACE_VEHICLE=1` diagnostic reads actually bound GPU buffers and views at one main vehicle draw; zero/null or unused trailing values are not automatically errors.

Validation: six recovery unit tests pass. Standard Release builds report zero errors. All 1,254 base outputs are valid, with 4,913 indexed native entries after exact recovered permutations replace their authored technique permutations. Hardware and WARP debug probes preload that index and find both shaders for all 1,020 recovered techniques. Both alloy prepasses read back packed normal RGBA (127 or 128, 127 or 128, 255, 0) and depth -0.200000 for the defined test triangle. The final tracing-disabled queued Showroom run exits zero in nine seconds; `showroom_delivery.png` visibly has a complete car body and shaded wheels, unlike the wheels-only baseline. Background geometry/textures and lighting remain substantially wrong. Some nonidentified draws still log no vertex shader with an empty last-FX error; no effect-lookup, parameter/texture-binding or layout failure lines appear in that final log. No overall visual parity is claimed.

Next: keep Showroom as the first test. Inspect an affected building draw's actual shader, declaration, constants and sampled textures, including integer/normalized vertex formats and the sRGB contract. Use the original source/retail evidence to resolve it. Extend vehicle recovery only from correctly keyed new captures; do not reuse the historical unkeyed dump as permutation evidence. The effect compiler now reuses authored binaries only when source, included headers, manifest and compiler freshness checks pass; recovered sources compile separately and all metadata is regenerated.

### T127: format-dependent alpha-test comparison recovered and implemented (2026-10-03)

Found in / Belongs to **Blur1PCDX11**. The D3D9 HAL format matrix (`_work/build/alpha_format_matrix_oct03/`, NVIDIA RTX 5070 Ti, driver nvldumd.dll) drew the same R32F alpha ramp through ALPHAFUNC 1-8 and ALPHAREF 0-255 into nine render-target formats. One rule reproduces all 524,288 samples of every format (`fit_final.py`):

- The reference is `float32(ref) * float32(1/255)`. Plain division by 255 misses 504 float32 samples.
- The output alpha and the reference are both converted to render target 0's precision before the compare. Formats without an alpha channel (X8R8G8B8, R16F, G16R16F, R32F) follow the class of their colour channels.
- UNORM with k bits (A8R8G8B8, X8R8G8B8: k=8; A2R10G10B10: k=10; A16B16G16R16: k=16): `u = min(floor(saturate(v) * 2^(k+4)), 2^(k+4)-1)`, then `(u * (2^k-1) + 2^(k+3) - 1) >> (k+4)`. The value is fixed to k+4 bits first, then rounded with ties going down: for 8 bits, u=2048 (127.5) gives 127.
- Float16 targets: truncate the float32 bits to half precision (clear the low 13 mantissa bits), unclamped. Clamping first misses 960 samples.
- Float32 targets: no conversion.

Native implementation: `alpha_test.py` converts both values in `BlurPCAlphaConvert`, selected by a new `BlurPCAlphaFormat` field in the b13 buffer. `BindRenderTargets` sets that field from render target 0's DXGI format (`AlphaTestFormat`), and `SetAlphaTestRef` computes the reference as above. Unmeasured target formats compare unconverted and log `DX11 alpha test unmeasured target format` (unverified). The 16-bit UNORM path sums the 36-bit product in 16-bit halves; the uint32 emulation matches the exact formula for every u at k=8, 10 and 16.

Verification: `_work/build/alpha_native_matrix_oct03/` replays the matrix through the generated HLSL. Hardware and WARP match D3D9 with zero mismatches on all nine formats. The control run with conversion forced off misses 65,784 (8-bit), 16,764 (10-bit), 1,524 (16-bit UNORM) and 4,988 (float16) samples and matches float32. The standard build regenerated all 4,913 indexed effects and the built-in shaders (errsum 0); EXE/PDB and effects were delivered with hash checks. Queued Observatory native-60 and unlocked races exit 0 (171 s, wait 0). Their targets are formats 10, 41, 87 and 90, all measured classes, and no unmeasured format is logged.

On the 8-bit Blur1PCDX11 target the NaN is written as 0 (dark specks where retail drew lit pixels); in the HDR child's FP16 scene it reaches the bright pass, and the bloom blur and lens-ghost pass spread it into flashes, mirrored through the screen centre onto the area in front of the car. The crowd and its flags line the start/finish straight. Fix: `sqrt(abs())` under `BLUR_DX11`, as `ExposureGamma` already does in the HDR child. With it the same lap had 0 NaN frames. The remaining bright-pass spikes are finite HDR highlights (single texels near the horizon, exhaust flames), also present before the fix; the white glow under the arch appears with HDR output off as well.

## T255 - full screen at a non-16:9 mode was stretched by DXGI (2026-10-23)
Reported: full screen 3840x1080 on the user's 16:9 3840x2160 TV showed the 32:9 image stretched to 16:9; Blur1PC (D3D9) letterboxes it. The rendered frame was correct (T254 aspect); the stretch happened in display scaling.
Measured with probes in `_work/uw_probe` (QueryDisplayConfig target scaling while each path holds the screen, NVIDIA RTX 5070 Ti): D3D9 exclusive 3840x1080 sets the mode with scaling 4 (`DISPLAYCONFIG_SCALING_ASPECTRATIOCENTEREDMAX`, the driver default). DXGI lists 3840x1080 as UNSPECIFIED, CENTERED and STRETCHED variants (16:9 modes only as UNSPECIFIED), and `FindClosestMatchingMode` resolves any UNSPECIFIED request for it to STRETCHED, for every refresh rate. The FP16 flip chain with `SetFullscreenState` + `ResizeTarget` (UNSPECIFIED, or the exact enumerated UNSPECIFIED mode) and the SDR blt chain created full screen both left the desktop at 3840x2160 with identity scaling, so the 3840x1080 buffer was stretched to the panel. CENTERED gives a real 3840x1080 mode but no scaling (matches D3D9 only when the width equals the panel's); STRETCHED landed on an unrelated 2560x1600 mode. `ChangeDisplaySettingsEx(CDS_FULLSCREEN)` sets 3840x1080 with scaling 4, as D3D9, and a windowed flip chain in a covering popup keeps it; `SetFullscreenState` fails (887a0022) once that mode is set.
Fix: `C_PCD3D11GameDevice` never uses DXGI full screen. Full screen sets the display mode with `ChangeDisplaySettingsEx(CDS_FULLSCREEN)` on the window's monitor and covers it with the popup; the swap chain is always created windowed (flip, blt fallback). As D3D9 exclusive mode does, losing activation restores the desktop mode and minimises the window, and reactivation sets the mode again (a `WM_ACTIVATEAPP` hook on the game window); DestroyDevice and windowed resets restore the desktop mode. Verified: full screen 3840x1080 Speed run reports `DX11 full screen mode \\.\DISPLAY1 3840x1080@0 result 0`, the monitor reads 3840x1080 with scaling 4 for the whole run and 3840x2160 again after exit; HDR output stays active (float=1).
